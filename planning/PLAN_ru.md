# FinAlly — торговый терминал с ИИ

## Спецификация проекта

## 1. Видение

FinAlly (Finance Ally — «финансовый союзник») — визуально эффектный торговый терминал на базе ИИ **для российского фондового рынка (Московская биржа, MOEX)**, который транслирует рыночные данные в реальном времени, позволяет торговать симулированным портфелем и включает чат-ассистента на основе LLM, способного анализировать позиции и совершать сделки от имени пользователя. Он выглядит и ощущается как современный терминал Bloomberg с ИИ-вторым пилотом.

Это итоговый проект курса по агентному программированию с ИИ. Он целиком создаётся агентами-программистами и демонстрирует, как оркестрованные ИИ-агенты могут построить full-stack приложение производственного качества. Агенты взаимодействуют через файлы в `planning/`.

## 2. Пользовательский опыт

### Первый запуск

Пользователь выполняет одну команду Docker (или предоставленный скрипт запуска). Браузер открывает `http://localhost:8000`. Без входа, без регистрации. Пользователь сразу видит:

- Список наблюдения (watchlist) из 10 тикеров Мосбиржи по умолчанию с обновляющимися в реальном времени ценами в виде сетки
- ₽10 000 виртуальных денег
- Тёмную, насыщенную данными эстетику торгового терминала
- Панель ИИ-чата, готовую помочь

### Что может делать пользователь

- **Следить за потоком цен** — цены вспыхивают зелёным (рост) или красным (падение) с мягкой затухающей CSS-анимацией
- **Смотреть мини-графики (sparklines)** — динамика цены рядом с каждым тикером в списке наблюдения, накапливаемая на фронтенде из SSE-потока с момента загрузки страницы (графики заполняются постепенно)
- **Кликнуть по тикеру**, чтобы увидеть крупный детальный график в основной области графика
- **Покупать и продавать акции** — только рыночные ордера, мгновенное исполнение по текущей цене, без комиссий, без диалога подтверждения
- **Отслеживать портфель** — тепловая карта (treemap), где позиции размером соответствуют весу и окрашены по P&L, плюс график P&L, отслеживающий общую стоимость портфеля во времени
- **Просматривать таблицу позиций** — тикер, количество, средняя цена покупки, текущая цена, нереализованный P&L, изменение в %
- **Общаться с ИИ-ассистентом** — спрашивать о портфеле, получать анализ, поручать ИИ совершать сделки и управлять списком наблюдения на естественном языке
- **Управлять списком наблюдения** — добавлять/удалять тикеры вручную или через ИИ-чат

### Визуальный дизайн

- **Тёмная тема**: фон около `#0d1117` или `#1a1a2e`, приглушённые серые границы, без чистого чёрного
- **Анимация вспышки цены**: кратковременная зелёная/красная подсветка фона при изменении цены, затухающая примерно за 500 мс через CSS transitions
- **Индикатор соединения**: маленькая цветная точка (зелёная = подключено, жёлтая = переподключение, красная = отключено) в шапке
- **Профессиональная, плотная по данным компоновка**: в духе Bloomberg/торговых терминалов — каждый пиксель на счету
- **Адаптивность с приоритетом десктопа**: оптимизировано для широких экранов, работоспособно на планшете

### Цветовая схема
- Акцентный жёлтый: `#ecad0a`
- Основной синий: `#209dd7`
- Вторичный фиолетовый: `#753991` (кнопки отправки)

## 3. Обзор архитектуры

### Один контейнер, один порт

```
┌─────────────────────────────────────────────────┐
│  Docker-контейнер (порт 8000)                   │
│                                                 │
│  FastAPI (Python/uv)                            │
│  ├── /api/*          REST-эндпоинты             │
│  ├── /api/stream/*   SSE-стриминг               │
│  └── /*              Раздача статических файлов │
│                      (экспорт Next.js)          │
│                                                 │
│  База SQLite (смонтированный том)               │
│  Фоновая задача: опрос/симуляция рынка          │
└─────────────────────────────────────────────────┘
```

- **Фронтенд**: Next.js с TypeScript, собранный как статический экспорт (`output: 'export'`), раздаётся FastAPI как статические файлы
- **Бэкенд**: FastAPI (Python), управляется как проект `uv`
- **База данных**: SQLite, один файл `db/finally.db`, смонтирован как том для сохранности данных
- **Данные в реальном времени**: Server-Sent Events (SSE) — проще WebSocket, односторонняя передача сервер→клиент, работает везде
- **Интеграция ИИ**: LiteLLM → OpenRouter (Cerebras для быстрого инференса), со структурированными выводами для исполнения сделок
- **Рыночные данные**: управляются переменной окружения — симулятор по умолчанию, реальные данные с Мосбиржи (MOEX) при включении

### Почему такие решения

| Решение | Обоснование |
|---|---|
| SSE вместо WebSocket | Нужна только односторонняя передача; проще, без двунаправленной сложности, универсальная поддержка браузерами |
| Статический экспорт Next.js | Один источник (origin), нет проблем с CORS, один порт, один контейнер, простое развёртывание |
| SQLite вместо Postgres | Нет аутентификации = нет многопользовательского режима = не нужен сервер БД; автономно, без настройки |
| Один Docker-контейнер | Студенты запускают одну команду; без docker-compose в продакшене, без оркестрации сервисов |
| uv для Python | Быстрое современное управление Python-проектами; воспроизводимый lock-файл; то, что стоит изучить студентам |
| Только рыночные ордера | Исключает книгу заявок, логику лимитных ордеров, частичные исполнения — резко упрощает математику портфеля |

### Ключевые границы

- **`frontend/`** — самостоятельный проект Next.js. Он ничего не знает о Python. Он общается с бэкендом через эндпоинты `/api/*` и SSE-эндпоинты `/api/stream/*`. Внутренняя структура — на усмотрение агента Frontend Engineer.
- **`backend/`** — самостоятельный проект uv со своим `pyproject.toml`. Он отвечает за всю серверную логику, включая инициализацию БД, схему, начальные данные, API-маршруты, SSE-стриминг, рыночные данные и интеграцию с LLM. Внутренняя структура — на усмотрение агентов Backend/Market Data.
- **`backend/db/`** содержит SQL-определения схемы и логику начального заполнения. Бэкенд инициализирует базу при старте — создаёт таблицы и заполняет данными по умолчанию, если файла SQLite нет или он пуст.
- **`db/`** на верхнем уровне — точка монтирования тома во время работы. Файл SQLite (`db/finally.db`) создаётся здесь бэкендом и сохраняется между перезапусками контейнера благодаря Docker-тому.
- **`planning/`** содержит общепроектную документацию, включая этот план. Все агенты используют файлы здесь как общий контракт.
- **`test/`** содержит E2E-тесты Playwright и вспомогательную инфраструктуру (например, `docker-compose.test.yml`). Модульные тесты находятся внутри `frontend/` и `backend/` соответственно, по соглашениям каждого фреймворка.
- **`scripts/`** содержит скрипты запуска/остановки, оборачивающие команды Docker.

## 5. Переменные окружения

```bash
# Обязательно, если не LLM_MOCK=true: ключ OpenRouter API для функций LLM-чата
OPENROUTER_API_KEY=your-openrouter-api-key-here

# Необязательно: "true", чтобы получать реальные цены с MOEX ISS API
# Если не задан (или "false"), используется встроенный симулятор рынка (рекомендуется большинству пользователей)
# Ключ API для MOEX не нужен — бесплатный/анонимный доступ не требует регистрации (см. MOEX_API.md)
MOEX_ENABLED=false

# Необязательно: "true" для детерминированных mock-ответов LLM (тестирование)
LLM_MOCK=false

# Необязательно: путь к файлу SQLite (по умолчанию: <корень_проекта>/db/finally.db; образ Docker задаёт /app/db/finally.db)
DB_PATH=
```

### Поведение

- Если `MOEX_ENABLED=true` → бэкенд использует MOEX ISS API для рыночных данных (реальные цены российских акций, задержка ~15 минут, ключ не нужен)
- Если `MOEX_ENABLED` отсутствует, пуст или не равен `"true"` → бэкенд использует встроенный симулятор рынка
- Если `LLM_MOCK=true` → бэкенд возвращает детерминированные mock-ответы LLM (для E2E-тестов)
- Бэкенд читает `.env` из корня проекта. Локально он загружается через `python-dotenv`; в Docker передаётся через `--env-file`

## 6. Рыночные данные

### Две реализации, один интерфейс

И симулятор, и клиент MOEX реализуют один и тот же абстрактный интерфейс. Бэкенд выбирает реализацию по переменной окружения `MOEX_ENABLED`. Весь нижележащий код (SSE-стриминг, кэш цен, фронтенд) не зависит от источника.

### Симулятор (по умолчанию)

- Генерирует цены с помощью геометрического броуновского движения (GBM) с настраиваемыми дрейфом и волатильностью для каждого тикера
- Обновляется с интервалом около 500 мс
- Коррелированные движения между тикерами (например, нефтегазовые акции движутся вместе)
- Случайные «события» — внезапные движения на 2–5% по тикеру для драматизма
- Стартует с реалистичных начальных цен (например, SBER ~₽273, GAZP ~₽97, LKOH ~₽5 315 и т. д. — см. список наблюдения по умолчанию в §7)
- Работает как фоновая задача внутри процесса — без внешних зависимостей

### MOEX ISS API (необязательно)

Полное исследование, на котором основан этот раздел (эндпоинты, проверенные примеры ответов, измерение 15-минутной задержки), — в `planning/MOEX_API.md`.

- Опрос REST API (не WebSocket) сервера `iss.moex.com` — проще, а собственный поток данных в реальном времени у MOEX всё равно требует платной подписки
- Ключ API или регистрация не нужны. Бесплатный/анонимный тариф отдаёт цены с задержкой ~15 минут, но они непрерывно обновляются (а не заморожены на конце дня)
- Опрашивает все отслеживаемые тикеры каждые 15 секунд одним запросом (`GET .../boards/TQBR/securities.json?securities=SBER,GAZP,...`) — MOEX не публикует официальный лимит запросов для анонимного доступа, поэтому этот интервал — консервативное значение «по умолчанию», а не измеренный потолок
- Разбирает REST-ответ в тот же формат, что и симулятор; тикеры, не найденные на доске TQBR (некорректный символ), возвращаются с пустым результатом, а не ошибкой — это обрабатывается так же, как «цены пока нет»

### Отслеживаемые тикеры

Источник рыночных данных отслеживает **список наблюдения ∪ тикеры с открытыми позициями**, поэтому открытые позиции продолжают получать цены, даже если их тикер удалён из списка наблюдения.

- При старте: `source.start(watchlist ∪ positions)`
- Добавление в список наблюдения (вручную, через чат или автоматически при сделке с неотслеживаемым тикером) → `source.add_ticker(ticker)`
- Удаление из списка наблюдения → `source.remove_ticker(ticker)`, только если по тикеру нет открытой позиции
- Позиция закрыта (продана до нуля) → `source.remove_ticker(ticker)`, только если тикера нет в списке наблюдения

**Неизвестные тикеры**: принимается любой символ из 1–5 букв (символы вроде `BRK.B` намеренно не поддерживаются; привилегированные акции MOEX вроде `SBERP` или `TATNP` естественно укладываются в это правило). Симулятор стартует неизвестные тикеры со случайной цены от ₽50 до ₽2000 с волатильностью по умолчанию — диапазон шире, чем понадобился бы для одной страны в долларах, потому что реальные тикеры MOEX и так охватывают диапазон от ~₽50 (VTBR) до более ₽5000 (LKOH). При работе с MOEX несуществующий символ просто никогда не получает цену (отображается как «—»; сделки по нему отклоняются).

### Общий кэш цен

- Одна фоновая задача (симулятор или опросчик MOEX) пишет в кэш цен в памяти
- Кэш хранит последнюю цену, предыдущую цену и метку времени для каждого тикера
- SSE-потоки читают из этого кэша и отправляют обновления подключённым клиентам
- Такая архитектура поддерживает будущие многопользовательские сценарии без изменений в слое данных

### SSE-стриминг

- Эндпоинт: `GET /api/stream/prices`
- Долгоживущее SSE-соединение; клиент использует нативный API `EventSource`
- Сервер проверяет кэш цен примерно каждые 500 мс и отправляет одно событие со **всеми отслеживаемыми тикерами**, если что-то изменилось
- Клиент обрабатывает переподключение автоматически (у EventSource есть встроенные повторные попытки; сервер отправляет `retry: 1000`)

Формат события (реализован в `backend/app/market/stream.py`) — одно сообщение `data:` со словарём, ключи которого — тикеры:

```
data: {"SBER": {"ticker": "SBER", "price": 273.5, "previous_price": 273.32, "timestamp": 1790000000.123, "change": 0.18, "change_percent": 0.0658, "direction": "up"}, "GAZP": {...}}
```

- `timestamp` — Unix-время в секундах (float)
- `change` / `change_percent` — относительно предыдущего тика (не дневное)
- `direction` — `"up"`, `"down"` или `"flat"`

## 7. База данных

### SQLite с инициализацией при старте

Бэкенд проверяет базу SQLite при старте (в обработчике lifespan FastAPI). Если файла нет или отсутствуют таблицы, он создаёт схему и заполняет данные по умолчанию. Это означает:

- Нет отдельного шага миграции
- Нет ручной настройки базы данных
- Новые Docker-тома автоматически стартуют с чистой заполненной базой

### Порядок запуска и остановки

Обработчик lifespan FastAPI выполняет по порядку:

1. Инициализирует базу данных (схема + начальные данные)
2. Загружает список наблюдения ∪ позиции
3. Создаёт источник рыночных данных и выполняет `await source.start(...)` (источник MOEX здесь делает один блокирующий опрос)
4. Записывает стартовый снимок портфеля
5. Запускает 30-секундную задачу снимков

При остановке: отменяет задачу снимков, затем `await source.stop()`.

### Соглашения

- Все сохраняемые метки времени — UTC ISO-8601 с суффиксом `Z`. Фронтенд переводит их в Unix-секунды для Lightweight Charts.
- Путь к базе берётся из `DB_PATH` (§5).

### Схема

Все таблицы, кроме `users_profile`, содержат столбец `user_id` со значением по умолчанию `"default"` (`users_profile` использует сам идентификатор пользователя в столбце `id`). Сейчас это значение зашито (один пользователь), но позволяет в будущем поддержать нескольких пользователей без миграции схемы.

**users_profile** — состояние пользователя (баланс денежных средств)
- `id` TEXT PRIMARY KEY (по умолчанию: `"default"`)
- `cash_balance` REAL (по умолчанию: `10000.0`)
- `created_at` TEXT (метка времени ISO)

**watchlist** — тикеры, за которыми следит пользователь
- `id` TEXT PRIMARY KEY (UUID)
- `user_id` TEXT (по умолчанию: `"default"`)
- `ticker` TEXT
- `added_at` TEXT (метка времени ISO)
- Ограничение UNIQUE на `(user_id, ticker)`

**positions** — текущие позиции (одна строка на тикер на пользователя)
- `id` TEXT PRIMARY KEY (UUID)
- `user_id` TEXT (по умолчанию: `"default"`)
- `ticker` TEXT
- `quantity` REAL (поддерживаются дробные акции)
- `avg_cost` REAL
- `updated_at` TEXT (метка времени ISO)
- Ограничение UNIQUE на `(user_id, ticker)`
- Строка удаляется, когда продажа доводит округлённое `quantity` до 0 (см. «Правила сделок»)

**trades** — история сделок (журнал только для добавления)
- `id` TEXT PRIMARY KEY (UUID)
- `user_id` TEXT (по умолчанию: `"default"`)
- `ticker` TEXT
- `side` TEXT (`"buy"` или `"sell"`)
- `quantity` REAL (поддерживаются дробные акции)
- `price` REAL
- `executed_at` TEXT (метка времени ISO)

**portfolio_snapshots** — стоимость портфеля во времени (для графика P&L). Записывается один раз при старте (чтобы график никогда не был пустым), каждые 30 секунд фоновой задачей и сразу после исполнения каждой сделки.
- `id` TEXT PRIMARY KEY (UUID)
- `user_id` TEXT (по умолчанию: `"default"`)
- `total_value` REAL
- `recorded_at` TEXT (метка времени ISO)

**chat_messages** — история переписки с LLM
- `id` TEXT PRIMARY KEY (UUID)
- `user_id` TEXT (по умолчанию: `"default"`)
- `role` TEXT (`"user"` или `"assistant"`)
- `content` TEXT
- `actions` TEXT (JSON — исполненные сделки, внесённые изменения в список наблюдения; null для сообщений пользователя)
- `created_at` TEXT (метка времени ISO)

### Начальные данные по умолчанию

- Один профиль пользователя: `id="default"`, `cash_balance=10000.0` (отображается как ₽10 000)
- Десять записей в списке наблюдения (все на доске TQBR Мосбиржи — обычные акции): SBER, GAZP, LKOH, GMKN, ROSN, NVTK, MTSS, TATN, PLZL, VTBR — Сбербанк, Газпром, Лукойл, Норникель, Роснефть, Новатэк, МТС, Татнефть, Полюс и ВТБ, охватывающие банковский сектор, нефтегаз, металлургию/добычу и телеком

### Форматы ответов

Ошибки используют стандартный формат FastAPI `{"detail": "<понятное сообщение>"}`: 400 — нарушение бизнес-правил, 404 — ресурс не найден, 422 — некорректное тело запроса (отсутствующие поля или неверные JSON-типы).

Модели запросов содержат только типы (`ticker: str`, `quantity: float`, `side: str`). Вся проверка правил (формат тикера, side, quantity) находится в общем сервисе сделок/списка наблюдения и выдаёт 400, поэтому ручные действия и действия LLM используют один путь кода. Эндпоинты POST и DELETE возвращают 200 с телом (никогда 201/204).

**`GET /api/portfolio`**
```json
{
  "cash_balance": 8100.0,
  "total_value": 10050.25,
  "unrealized_pnl": 50.25,
  "positions": [
    {"ticker": "SBER", "quantity": 10, "avg_cost": 270.0, "current_price": 275.03,
     "market_value": 2750.3, "unrealized_pnl": 50.3, "pnl_percent": 1.86}
  ]
}
```
- `total_value` = `cash_balance` + Σ `market_value`; `pnl_percent` = (`current_price` − `avg_cost`) / `avg_cost` × 100
- Если у удерживаемого тикера ещё нет цены (например, сразу после старта с MOEX), `current_price` равен `null`, а позиция оценивается по `avg_cost` (`market_value` = количество × `avg_cost`, P&L = 0). То же правило действует для снимков и контекста LLM.
- Шапка фронтенда использует живые цены SSE, поэтому может немного отличаться от `total_value` бэкенда. Это ожидаемо.
- Денежные поля (`cash_balance`, `total_value`, цены и т. д.) — обычные числа, в рублях; фронтенд отображает их со знаком `₽`.

**`POST /api/portfolio/trade`** — запрос `{"ticker": "SBER", "quantity": 10, "side": "buy"}`; ответ 200:
```json
{
  "trade": {"id": "uuid", "ticker": "SBER", "side": "buy", "quantity": 10, "price": 270.0,
            "executed_at": "2026-09-28T10:00:00Z"},
  "portfolio": { "...тот же формат, что у GET /api/portfolio..." }
}
```
Пример ошибки (400): `{"detail": "Insufficient cash: need ₽53,150.00, have ₽10,000.00"}`

**`GET /api/portfolio/history`** — от старых к новым:
```json
[{"total_value": 10000.0, "recorded_at": "2026-09-28T10:00:00Z"}]
```

**`GET /api/watchlist`**, **`POST /api/watchlist`**, **`DELETE /api/watchlist/{ticker}`** — все возвращают текущий список наблюдения, упорядоченный по `added_at`:
```json
["SBER", "GAZP", "LKOH"]
```
- POST: 400, если тикер не состоит из 1–5 букв; добавление уже существующего тикера ничего не меняет
- DELETE: параметр пути `{ticker}` также очищается от пробелов и приводится к верхнему регистру; 404, если тикера нет в списке наблюдения

**`POST /api/chat`** — запрос `{"message": "Buy 10 SBER"}`; ответ 200:
```json
{
  "message": "Done — bought 10 SBER at ₽270.00.",
  "actions": {
    "trades": [
      {"ticker": "SBER", "side": "buy", "quantity": 10, "status": "executed", "price": 270.0},
      {"ticker": "LKOH", "side": "buy", "quantity": 10, "status": "failed", "error": "Insufficient cash: ..."}
    ],
    "watchlist_changes": [
      {"ticker": "YDEX", "action": "add", "status": "executed"}
    ]
  }
}
```
Тот же JSON `actions` сохраняется в `chat_messages.actions`.

Результаты изменений списка наблюдения: добавление уже существующего тикера — `executed` (ничего не меняет, как в REST-эндпоинте); удаление тикера, которого нет в списке, или добавление некорректного символа — `failed` с полем `error`.

**`GET /api/chat/history`** — от старых к новым; `actions` равно `null` для сообщений пользователя:
```json
[
  {"role": "user", "content": "Buy 10 SBER", "actions": null, "created_at": "2026-09-28T10:00:00Z"},
  {"role": "assistant", "content": "Done — bought 10 SBER at ₽270.00.", "actions": {"trades": [], "watchlist_changes": []}, "created_at": "2026-09-28T10:00:01Z"}
]
```

**`GET /api/health`** → `{"status": "ok"}`

### Правила сделок

Применяются одинаково к ручным сделкам и сделкам LLM:

Проверки выполняются в таком порядке, поэтому неудачная сделка не имеет побочных эффектов:

1. `ticker` очищается от пробелов, приводится к верхнему регистру и должен состоять из 1–5 букв; `side` должен быть `"buy"` или `"sell"`
2. `quantity` округляется до 4 знаков после запятой (дробные акции допускаются), затем должно быть > 0
3. Только продажа: `quantity` ≤ количества в позиции (сравнение после округления)
4. Если тикер не отслеживается, он добавляется в список наблюдения (так же, как через `POST /api/watchlist`). Симулятор сразу назначает ему цену; при работе с MOEX цена приходит со следующим опросом (до 15 с)
5. У тикера должна быть текущая цена в кэше — иначе 400 (`"No price available for XYZ yet, try again shortly"`)
6. Только покупка: `quantity × price` ≤ `cash_balance`

Исполнение:

- Покупка: новый `avg_cost` = (old_qty × old_avg + qty × price) / (old_qty + qty)
- Продажа: `avg_cost` не меняется; строка позиции удаляется, когда итоговое количество ≤ 0
- Итоговое количество округляется до 4 знаков, а `cash_balance` — до центов после каждой сделки, чтобы избежать накопления погрешности float
- Каждая сделка выполняется в одной транзакции SQLite под единым `asyncio.Lock` в сервисе сделок, поэтому параллельные ручные сделки и сделки из чата не перемешиваются
- Каждая исполненная сделка добавляется в `trades` и записывает снимок портфеля

## 9. Интеграция с LLM

При написании кода для вызовов LLM используйте навык cerebras-inference, чтобы через LiteLLM и OpenRouter обращаться к модели `openrouter/openai/gpt-oss-120b` с Cerebras в качестве провайдера инференса. Для интерпретации результатов следует использовать структурированные выводы (Structured Outputs).

В файле .env в корне проекта есть OPENROUTER_API_KEY.

### Как это работает

Когда пользователь отправляет сообщение в чат, бэкенд:

1. Загружает текущий контекст портфеля пользователя (деньги, позиции с P&L, список наблюдения с текущими ценами, общая стоимость портфеля)
2. Загружает последние 20 сообщений истории переписки из таблицы `chat_messages`. К каждому сообщению ассистента добавляется краткая сводка его `actions`, например `[actions: bought 10 SBER @270.00; LKOH buy failed: Insufficient cash]`, чтобы LLM видела прошлые неудачи
3. Формирует промпт с системным сообщением, контекстом портфеля, историей переписки и новым сообщением пользователя
4. Вызывает LLM через LiteLLM → OpenRouter, запрашивая структурированный вывод, с помощью навыка cerebras-inference. Вызов не должен блокировать цикл событий: используйте `litellm.acompletion` (или оберните синхронный вызов в `asyncio.to_thread`), иначе SSE и симулятор зависнут, пока модель отвечает
5. Разбирает полный структурированный JSON-ответ
6. Автоматически исполняет указанные в ответе сделки или изменения списка наблюдения
7. Сохраняет в `chat_messages` сообщение пользователя и сообщение ассистента с результатами исполнения (`actions`)
8. Возвращает полный JSON-ответ фронтенду (формат в §8; без потоковой передачи по токенам — инференс Cerebras достаточно быстр, чтобы хватило индикатора загрузки)

### Схема структурированного вывода

LLM получает инструкцию отвечать JSON-ом, соответствующим этой схеме:

```json
{
  "message": "Your conversational response to the user",
  "trades": [
    {"ticker": "SBER", "side": "buy", "quantity": 10}
  ],
  "watchlist_changes": [
    {"ticker": "YDEX", "action": "add"}
  ]
}
```

Все три поля обязательны (строгий структурированный вывод, без лишних свойств); массивы пусты, если не используются. Определите её одной моделью Pydantic: `side: Literal["buy", "sell"]`, `action: Literal["add", "remove"]`, `quantity: float`. Значение неверного типа (например, `"10"` вместо числа в `quantity`) — это ошибка разбора, приведение типов не выполняется.

- `message`: разговорный текст, показываемый пользователю
- `trades`: массив сделок для автоисполнения. `side` — `"buy"` или `"sell"`. Каждая сделка проходит те же правила сделок, что и ручные (§8)
- `watchlist_changes`: массив изменений списка наблюдения. `action` — `"add"` или `"remove"`

Если вызов LLM завершился ошибкой или вернул неразбираемый ответ, эндпоинт возвращает короткое извинение в `message`, пустые `actions`, и ничего не исполняется.

### Автоисполнение

Сделки, указанные LLM, исполняются автоматически — без диалога подтверждения. Это сознательное проектное решение:
- Это симулированная среда с ненастоящими деньгами, так что ставки нулевые
- Это создаёт впечатляющий, плавный демонстрационный опыт
- Это демонстрирует возможности агентного ИИ — основную тему курса

На каждое сообщение делается один вызов LLM, поэтому `message` написан до исполнения. Если сделка не проходит проверку (например, недостаточно денег), бэкенд помечает её `"status": "failed"` с полем `error` в `actions`, а фронтенд показывает это прямо рядом с сообщением. Второго вызова LLM нет. Неудачные действия сохраняются в истории, поэтому LLM видит их в следующих репликах.

### Рекомендации для системного промпта

LLM следует представлять как «FinAlly, ИИ-ассистент по торговле на российском фондовом рынке (MOEX)» с инструкциями:
- Анализировать состав портфеля, концентрацию риска и P&L
- Предлагать сделки с обоснованием
- Исполнять сделки, когда пользователь просит или соглашается
- Проактивно управлять списком наблюдения
- Отвечать кратко и с опорой на данные
- Всегда отвечать валидным структурированным JSON

### Mock-режим LLM

При `LLM_MOCK=true` бэкенд возвращает детерминированные mock-ответы вместо вызова OpenRouter. Затем mock-ответ проходит обычный процесс исполнения. Правила (проверка сообщения пользователя без учёта регистра):

- Содержит `"buy"` → `message: "Mock: buying 1 share of SBER."`, `trades: [{"ticker": "SBER", "side": "buy", "quantity": 1}]`
- Содержит `"sell"` → `message: "Mock: selling 1 share of SBER."`, `trades: [{"ticker": "SBER", "side": "sell", "quantity": 1}]`
- Если совпадают оба правила, приоритет у `"buy"`
- Иначе → `message: "Mock: this is a test response."`, без действий

Это позволяет:
- Быстрые, бесплатные, воспроизводимые E2E-тесты
- Разработку без API-ключа
- Конвейеры CI/CD

## 10. Дизайн фронтенда

### Компоновка

Фронтенд — одностраничное приложение с плотной компоновкой в стиле терминала. Конкретная архитектура компонентов и система компоновки — на усмотрение Frontend Engineer, но интерфейс должен включать следующие элементы:

- **Панель списка наблюдения** — сетка/таблица отслеживаемых тикеров (из `GET /api/watchlist`, объединённых с ценами из SSE) с: символом тикера, текущей ценой (вспыхивает зелёным/красным при изменении), изменением за сессию в % и мини-графиком (накапливается из SSE с момента загрузки страницы). Изменение за сессию в % = изменение относительно первой цены, полученной по тикеру после загрузки страницы (у симулятора нет дневного открытия).
- **Основная область графика** — крупный график для выбранного тикера, как минимум цена во времени. Клик по тикеру в списке наблюдения выбирает его здесь.
- **Тепловая карта портфеля** — визуализация treemap, где каждый прямоугольник — позиция, размер соответствует весу в портфеле, цвет — P&L (зелёный = прибыль, красный = убыток)
- **График P&L** — линейный график общей стоимости портфеля во времени по данным из `portfolio_snapshots`
- **Таблица позиций** — табличное представление всех позиций: тикер, количество, средняя цена покупки, текущая цена, нереализованный P&L, изменение в %
- **Торговая панель** — простая область ввода: поле тикера, поле количества, кнопка покупки, кнопка продажи. Рыночные ордера, мгновенное исполнение.
- **Панель ИИ-чата** — закреплённая/сворачиваемая боковая панель. При загрузке страницы подгружает прошлые сообщения из `GET /api/chat/history`. Поле ввода сообщения, прокручиваемая история переписки, индикатор загрузки во время ожидания ответа LLM. Исполненные сделки и изменения списка наблюдения показываются прямо в переписке как подтверждения.
- **Шапка** — общая стоимость портфеля (обновляется в реальном времени), индикатор соединения, баланс денежных средств

### Технические заметки

- Использовать `EventSource` для SSE-соединения с `/api/stream/prices`
- Текущие значения портфеля вычисляются на фронтенде: общая стоимость в шапке = деньги + Σ количество × последняя цена из SSE; таблица позиций и тепловая карта используют те же текущие цены. Портфель запрашивается из `GET /api/portfolio` при загрузке и повторно после каждой сделки и ответа чата
- Графики:
  - **Lightweight Charts** (canvas) для основного графика цены и графика P&L
  - **Recharts `Treemap`** для тепловой карты портфеля
  - **Inline SVG polyline** для мини-графиков (без библиотеки)
- Эффект вспышки цены: при получении новой цены кратко применить CSS-класс с переходом цвета фона, затем убрать его. Направление определяется сравнением с последней отрисованной на фронтенде ценой этого тикера, а не полем `direction` события (серверные тики могут объединяться или пропускаться)
- Все API-вызовы идут на тот же источник (`/api/*`) — настройка CORS не нужна
- Форматирование валюты: все денежные значения (деньги, цены, P&L) приходят из API обычными числами, в рублях. Фронтенд форматирует их с префиксом `₽`, например `₽10 000,00` — никакой другой локализации валюты не требуется
- Локальная разработка: `output: 'export'` не поддерживает rewrites в `next dev`, поэтому порядок такой: `npm run build`, а FastAPI раздаёт `frontend/out` (в Docker — из `backend/static`, см. §11)
- Tailwind CSS для стилизации с собственной тёмной темой

## 11. Docker и развёртывание

### Многоэтапный Dockerfile

```
Этап 1: Node 24 slim (LTS)
  - Скопировать frontend/
  - npm install && npm run build (создаёт статический экспорт)

Этап 2: Python 3.12 slim
  - Установить uv (COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/)
  - Скопировать backend/
  - uv sync --frozen --no-dev (установить Python-зависимости из lock-файла)
  - Скопировать результат сборки фронтенда в backend/static/
  - Открыть порт 8000
  - CMD: uvicorn, обслуживающий приложение FastAPI
```

FastAPI обслуживает все API-маршруты на порту 8000 и монтирует `backend/static` через `StaticFiles(html=True)` в `/`, регистрируя это после всех роутеров `/api`.

### Docker-том

База SQLite сохраняется через именованный Docker-том:

```bash
docker run -v finally-data:/app/db -p 8000:8000 --env-file .env finally
```

Каталог `db/` в корне проекта соответствует `/app/db` в контейнере. Бэкенд записывает `finally.db` по этому пути через `DB_PATH=/app/db/finally.db` (задаётся в Dockerfile). Локально по умолчанию используется `<корень_проекта>/db/finally.db`, а не `backend/db/`, где лежит код схемы.

### Скрипты запуска/остановки

**`scripts/start.sh`** (macOS/Linux):
- Собирает Docker-образ, если он ещё не собран (или если передан флаг `--build`)
- Запускает контейнер с монтированием тома, пробросом порта и файлом `.env`
- Выводит URL для доступа к приложению
- При желании открывает браузер

**`scripts/stop.sh`** (macOS/Linux):
- Останавливает и удаляет работающий контейнер
- НЕ удаляет том (данные сохраняются)

Все скрипты должны быть идемпотентными — безопасными при многократном запуске.

### Необязательное облачное развёртывание

Контейнер рассчитан на развёртывание в AWS App Runner, Render или любой контейнерной платформе. Конфигурация Terraform для App Runner может быть предоставлена в каталоге `deploy/` как дополнительная цель, но не входит в основную сборку.

## 12. Стратегия тестирования

### Модульные тесты (внутри `frontend/` и `backend/`)

**Бэкенд (pytest)**:
- Рыночные данные: симулятор генерирует корректные цены, математика GBM верна, разбор ответов MOEX ISS API работает, обе реализации соответствуют абстрактному интерфейсу
- Портфель: логика исполнения сделок, расчёты P&L, граничные случаи (продажа больше, чем есть; покупка при недостатке денег; продажа в убыток)
- LLM: разбор структурированного вывода обрабатывает все валидные схемы, корректная обработка некорректных ответов, проверка сделок в потоке чата
- API-маршруты: правильные коды статуса, форма ответов, обработка ошибок

**Фронтенд (React Testing Library или аналог)**:
- Рендеринг компонентов с тестовыми данными
- Анимация вспышки цены корректно срабатывает при изменении цены
- CRUD-операции со списком наблюдения
- Расчёты для отображения портфеля
- Рендеринг сообщений чата и состояние загрузки

### E2E-тесты (в `test/`)

**Инфраструктура**: отдельный `docker-compose.test.yml` в `test/`, который поднимает контейнер приложения и контейнер Playwright. Это не даёт браузерным зависимостям попасть в продакшен-образ.

**Окружение**: по умолчанию тесты запускаются с `LLM_MOCK=true` ради скорости и детерминированности.

**Ключевые сценарии**:
- Чистый старт: появляется список наблюдения по умолчанию, отображается баланс ₽10k, цены транслируются
- Добавление и удаление тикера из списка наблюдения
- Покупка акций: деньги уменьшаются, появляется позиция, портфель обновляется
- Продажа акций: деньги увеличиваются, позиция обновляется или исчезает
- Визуализация портфеля: тепловая карта отображается с правильными цветами, на графике P&L есть точки данных
- ИИ-чат (mock): отправить сообщение, получить ответ, исполнение сделки отображается в переписке. Mock продаёт SBER, которого по умолчанию нет в портфеле, поэтому сценарий «sell» должен сначала купить
- Устойчивость SSE: заблокировать поток (`page.route('**/api/stream/prices', r => r.abort())` или `context.setOffline(true)`), проверить, что индикатор стал жёлтым/красным, восстановить соединение, проверить, что он стал зелёным
